# Промт для AntiGravity Agent — безопасная и полноценная админ-панель для Art Avenue Studio

## Главная задача

Ты работаешь с существующим сайтом:

**https://artavenue.studio**

Сайт будет открыт у тебя в браузере/окружении агента. Твоя задача — **изучить существующий проект и реализовать полноценную, безопасную и качественную CMS/админ-панель**, через которую можно будет управлять всем редактируемым контентом сайта.

Не создавай отдельный демонстрационный проект и не делай упрощённый прототип. Работай непосредственно с существующей архитектурой сайта и интегрируй админ-панель в неё.

Главный принцип:

> Обычный посетитель должен видеть сайт ровно так, как он выглядит сейчас, а авторизованный администратор должен видеть тот же сайт, но с дополнительными элементами управления редактированием.

Перед написанием кода:

1. Изучи весь существующий frontend.
2. Определи используемый стек.
3. Изучи структуру компонентов.
4. Определи все страницы сайта.
5. Найди все текстовые блоки.
6. Найди все карточки.
7. Найди изображения.
8. Найди существующие модальные окна.
9. Найди 3D-модели и компоненты, отвечающие за их отображение.
10. Изучи routing.
11. Изучи существующую систему хранения данных.
12. Определи, есть ли backend/API/database.
13. Определи, где и как сейчас хранятся изображения и 3D-файлы.
14. Не ломай существующий дизайн и функциональность.

**Не начинай реализацию, пока не поймёшь архитектуру проекта.**

Если для реализации админки необходим backend, database, storage или API — спроектируй их правильно и интегрируй в существующий проект.

Не используй временные решения вида:

- данные в localStorage;
- данные прямо в frontend-коде;
- захардкоженные пароли;
- публичные секретные ключи;
- хранение админского пароля в JavaScript;
- фиктивную авторизацию;
- Base64 для хранения больших файлов.

# 2. Архитектура админ-панели

Нужна отдельная защищённая зона администратора.

Например:

`/admin`

или другой маршрут, который лучше соответствует существующей архитектуре.

Админ-панель должна включать:

- страницу авторизации;
- dashboard;
- управление страницами;
- управление текстами;
- управление карточками;
- управление изображениями;
- управление 3D-моделями;
- предпросмотр изменений;
- сохранение изменений;
- возможность отменить изменения;
- состояния загрузки;
- обработку ошибок;
- валидацию данных.

# 3. Авторизация и безопасность

Это критически важная часть.

Админ-панель **не должна быть защищена только скрытым URL**.

Необходимо реализовать настоящую серверную авторизацию.

Требования:

- безопасная авторизация;
- пароль не должен находиться во frontend;
- секреты не должны попадать в Git;
- использовать environment variables;
- сервер должен самостоятельно проверять права администратора;
- API endpoints должны проверять authentication/authorization;
- нельзя доверять роли администратора, переданной клиентом;
- нельзя позволять обычному пользователю напрямую обращаться к admin API;
- защита от CSRF/XSS там, где это применимо;
- корректная обработка session/token;
- logout;
- защита admin routes;
- rate limiting для login/API, если архитектура позволяет;
- безопасные cookies, если используется cookie-based authentication;
- HttpOnly/Secure/SameSite для соответствующих cookies;
- валидация всех входных данных на сервере;
- проверка MIME type и размера загружаемых файлов;
- защита от загрузки исполняемых файлов под видом изображений;
- не допускать path traversal;
- не хранить пользовательские файлы непосредственно в публичной директории без контроля доступа.

После реализации проведи отдельную проверку безопасности.

# 4. Главная особенность интерфейса администратора

Это самое важное требование.

Когда обычный пользователь открывает:

`https://artavenue.studio`

он должен видеть обычный сайт без каких-либо элементов админки.

Когда авторизованный администратор открывает тот же сайт:

`https://artavenue.studio`

он должен видеть **тот же самый сайт**, с тем же дизайном, расположением элементов, анимациями и функциональностью.

Но поверх редактируемых элементов должны появляться аккуратные кнопки/индикаторы редактирования.

Например:

```text
[ ТЕКСТ ]
      ↓
┌─────────────────────────────┐
│ Заголовок существующего     │
│ текста на сайте          ✎  │
└─────────────────────────────┘
```

При наведении или нажатии появляется возможность:

**Редактировать**

Не нужно превращать сайт в громоздкий визуальный редактор.

Редактор должен ощущаться как дополнительный слой поверх существующего сайта.

# 5. Редактирование любого текста

Необходимо сделать так, чтобы **весь текстовый контент сайта можно было изменить через админку**.

Не ограничивайся только главными заголовками.

Найди и сделай редактируемыми:

- заголовки;
- подзаголовки;
- описания;
- обычные текстовые блоки;
- подписи;
- тексты кнопок;
- тексты в карточках;
- тексты модальных окон;
- FAQ;
- контакты;
- footer;
- navigation;
- любые другие текстовые элементы, которые являются контентом.

Не нужно делать редактируемыми технические строки интерфейса, если они не относятся к контенту.

---

# 6. Inline-редактирование

На сайте администратора возле каждого редактируемого текстового блока должна быть небольшая кнопка:

**✎**

или аналогичная иконка.

При нажатии открывается удобный редактор.

Редактор должен позволять:

- изменить текст;
- сохранить;
- отменить;
- показать текущее значение;
- показать состояние сохранения;
- показать ошибку при сохранении.

Если текст содержит форматирование, не уничтожай его.

Если в проекте используются:

- `<strong>`;
- ссылки;
- списки;
- переносы;
- выделения;

то редактор должен учитывать существующую структуру.

Не превращай всё в один огромный HTML textarea без необходимости.

# 7. Редактирование карточек

Все существующие карточки сайта должны стать управляемыми через админку.

Администратор должен иметь возможность открыть карточку и изменить **весь её контент**.

Например:

- заголовок;
- подзаголовок;
- описание;
- дополнительные тексты;
- кнопки;
- подписи;
- изображения;
- 3D-модель;
- порядок элементов;
- ссылки;
- содержимое модального окна.

Если карточка открывает modal, её modal также должен редактироваться.

Создай отдельный полноценный интерфейс:

**Редактировать карточку**

```text

[________________________]

[________________________]

Полное описание
[________________________]

[________________________]
```

Не ограничивайся этим набором. Составь структуру редактора исходя из реального содержимого существующих карточек сайта.

---

# 9. Редактирование модальных окон

Если карточка открывает модальное окно, администратор должен иметь возможность полностью изменить его содержимое.

Должна быть возможность менять:

- заголовок;
- основной текст;
- дополнительные блоки;
- изображения;
- 3D-модель;
- кнопки;
- ссылки;
- подписи.

При этом обычный пользователь должен продолжать видеть модальное окно в исходном дизайне сайта.

---

# 10. Работа с изображениями

В админке должна быть полноценная система загрузки изображений.

Администратор должен иметь возможность:

- выбрать файл;
- загрузить изображение;
- увидеть preview;
- заменить изображение;
- удалить изображение;
- выбрать существующее изображение;
- использовать изображение в конкретном месте сайта.

При загрузке необходимо выбирать назначение изображения.

Например:

```text
Тип изображения:

○ Изображение карточки
○ Изображение модального окна
○ Hero / Banner
○ Фоновое изображение
○ Галерея
○ Другое
```

Но список должен соответствовать реальным типам изображений проекта.

`/admin/media`

- список файлов;

- дата загрузки;
- где используется файл;

# 12. Поддержка 3D-моделей

Это отдельная важная часть.

В редакторе карточки должна быть возможность загрузить 3D-модель.

Перед загрузкой администратор должен видеть:

```text
3D-модель

Поддерживаемые форматы:

GLB
GLTF
OBJ
FBX
STL
```

**Но не добавляй поддержку формата только ради списка.**

Сначала изучи существующий 3D viewer сайта и его реальные возможности.

Если текущий viewer поддерживает только определённые форматы — используй именно реально поддерживаемые форматы.

Если возможно безопасно расширить поддержку — сделай это.

Особое внимание удели:

- `.glb`;
- `.gltf`;
- `.obj`;
- связанным texture files;
- размерам файлов;
- загрузке нескольких связанных файлов;
- корректному хранению assets.

Для форматов, которые невозможно нормально отобразить текущим viewer без конвертации, **не обещай поддержку просто в интерфейсе**.

Можно сделать backend-конвертацию только если это действительно оправдано архитектурой проекта.

---

# 13. Загрузка 3D-модели

При добавлении 3D-модели должно быть понятно:

```text
Добавить 3D-модель

Файл:
[ Выбрать ]

Формат:
GLB

Размер:
12.4 MB

Назначение:
[ Карточка №... ]

[Загрузить]
```

После загрузки:

- показать preview;
- показать название;
- показать формат;
- показать размер;
- позволить заменить;
- позволить удалить.

Если модель можно визуализировать прямо в админке — желательно показать preview через существующий viewer.

---

# 14. Не ломай существующий 3D viewer

Если на сайте уже существует компонент просмотра 3D-моделей:

**используй его повторно.**

Не создавай второй независимый viewer без необходимости.

Лучше сделать:

```text
Existing 3D Viewer
        ↓
получает model URL из CMS
```

Таким образом после замены модели через админку обычный сайт автоматически показывает новую модель.

---

# 15. CMS-структура

Не делай систему на десятках хаотичных переменных.

Нужна нормальная структура данных.

Например:

```text
Page
 ├── sections
 │    ├── texts
 │    ├── cards
 │    ├── images
 │    └── settings
 │
Card
 ├── title
 ├── description
 ├── image
 ├── model
 ├── modal
 └── settings
```

Но конкретную схему выбери после анализа проекта.

Она должна быть:

- расширяемой;
- типизированной;
- понятной;
- нормализованной там, где это необходимо;
- пригодной для дальнейшего добавления новых страниц.

---

# 16. Изменения должны применяться без изменения frontend-кода

Главная цель CMS:

Администратор меняет:

```text
Заголовок:
"Старый текст"
```

на:

```text
"Новый текст"
```

и обычный пользователь после обновления сайта видит:

```text
"Новый текст"
```

Без:

- изменения React-компонента;
- нового deploy;
- ручного изменения JSON;
- изменения исходного кода.

---

# 17. Draft / Publish

Если архитектура позволяет, реализуй систему:

**Draft → Preview → Publish**

То есть администратор может:

1. изменить данные;
2. посмотреть preview;
3. сохранить draft;
4. опубликовать изменения.

Обычные пользователи должны видеть только опубликованную версию.

Это особенно важно для большого количества изменений.

---

# 18. История изменений

Желательно добавить историю изменений.

Например:

```text
История

20.08.2026 09:31
Изменён заголовок Hero

20.08.2026 09:40
Изменена карточка "..."

20.08.2026 09:45
Заменена 3D-модель
```

Если это несложно реализовать в выбранной архитектуре — добавь.

Администратор должен иметь возможность понимать:

- что изменилось;
- когда;
- кем;
- какое значение было раньше.

---

# 19. UX админки

Админка должна выглядеть профессионально.

Не используй стандартные необработанные HTML-формы.

Нужны:

- sidebar;
- понятная навигация;
- dashboard;
- страницы редакторов;
- modal/dialog;
- toast notifications;
- loading states;
- empty states;
- error states;
- confirmation перед удалением;
- адаптивность.

Основной сайт при этом **не должен визуально меняться** для обычного пользователя.

---

# 20. Индикаторы редактирования

Для администратора:

- кнопки редактирования должны быть небольшими;
- не должны ломать layout;
- не должны влиять на размеры элементов;
- не должны мешать просмотру;
- должны исчезать для обычных пользователей.

Например:

```text
┌──────────────────────────┐
│ Заголовок           [✎]  │
└──────────────────────────┘
```

При hover можно показывать:

`Редактировать`

Не используй огромные рамки вокруг каждого элемента.

---

# 21. Админский режим

Сделай состояние:

```text
ADMIN MODE
```

Чтобы администратор явно понимал, что он находится в режиме редактирования.

Можно сделать небольшой floating control:

```text
┌────────────────────────────┐
│ ADMIN MODE     [Dashboard] │
│                [Logout]    │
└────────────────────────────┘
```

Он должен быть аккуратным и не мешать сайту.

---

# 22. Сохранение

После изменения текста:

```text
Сохранить
```

должно быть реальное сохранение в backend/database.

Показывать:

```text
Сохранение...
```

затем:

```text
Сохранено
```

При ошибке:

```text
Не удалось сохранить изменения.
Попробуйте ещё раз.
```

Нельзя показывать "Сохранено", если сервер реально не подтвердил изменение.

---

# 23. Валидация

Все формы должны валидироваться.

Проверять:

- обязательные поля;
- длину текста;
- допустимые форматы файлов;
- размер файлов;
- URL;
- структуру данных;
- существование связанных assets;
- допустимые значения.

Валидация должна быть **и на frontend, и на backend**.

---

# 24. Работа с файлами

Для файлов используй нормальное storage-решение.

Не сохраняй большие файлы непосредственно в database.

Архитектура должна быть примерно:

```text
Frontend
   ↓
Backend/API
   ↓
Storage
   ↓
Database → metadata
```

В database хранить:

- id;
- filename;
- URL/path;
- MIME;
- size;
- type;
- createdAt;
- relation;
- metadata.

---

# 25. Производительность

Не допускай, чтобы добавление CMS сильно замедлило обычный сайт.

Обычный посетитель:

- не должен загружать весь admin UI;
- не должен получать admin-only JavaScript без необходимости;
- не должен получать editor components;
- не должен делать запросы к admin API;
- не должен загружать media library.

Админские компоненты должны по возможности загружаться отдельно.

---

# 26. SEO

После внедрения CMS не сломай:

- title;
- meta description;
- headings;
- Open Graph;
- canonical;
- robots;
- sitemap;
- SEO-структуру.

Если title/description являются частью контента сайта — сделай их управляемыми через админку.

---

# 27. Responsive

Проверь:

- desktop;
- laptop;
- tablet;
- mobile.

Админка тоже должна нормально работать на небольших экранах, насколько это разумно.

---

# 28. Не меняй дизайн сайта без необходимости

Это принципиально.

Твоя задача — **не переделать Art Avenue Studio**, а добавить CMS.

Не меняй:

- цвета;
- шрифты;
- spacing;
- анимации;
- структуру;
- визуальный стиль;
- существующие компоненты;

если это не требуется для интеграции админки.

Если обнаружишь существующие проблемы — сначала оцени, могут ли они быть связаны с внедрением CMS.

# 29. Код

Код должен быть production-ready.

Требования:

- TypeScript, если проект использует TypeScript;
- строгая типизация;
- понятные названия;
- переиспользуемые компоненты;
- отсутствие дублирования;
- отсутствие мёртвого кода;
- отсутствие debug console.log;
- отсутствие hardcoded secrets;
- корректная обработка ошибок;
- server/client boundaries;
- нормальная структура API;
- понятные модели данных.

# 30. Не используй фиктивные данные

Запрещено делать:

```js
const content = {
  title: "..."
}
```

как основное постоянное хранилище CMS.

Также запрещено:

- localStorage как database;
- sessionStorage как database;
- hardcoded admin password;
- fake login;
- mock API вместо реального backend;
- временные заглушки в production-коде.

Если какая-либо часть действительно требует временной реализации — обозначь её отдельно и замени до завершения задачи.

```text
                 ART AVENUE STUDIO
                        │

             │                     │
        Обычный пользователь    Администратор
             │                     │
             ↓                     ↓
       Обычный сайт          Авторизация /admin
                                   │
                                   ↓
                              Admin Mode
                                   │
                                   ↓
                         Сайт + Edit Controls
                                   │
                 ┌─────────────────┼─────────────────┐
                 ↓                 ↓                 ↓
              Тексты            Карточки           Media
                                   │
                              ┌────┴────┐
                              ↓         ↓
                           Images     3D Models
                              │
                              ↓
                           Modals
```
